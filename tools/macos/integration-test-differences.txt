# Upstream's memory monitor (host_tools/memory.py) fails a test whose VMM
# holds more than 5 MiB resident besides guest memory (7 MiB while a
# snapshot is taken). On macOS the VMM's own memory is at that budget: the
# process's regions as wick_macos.memory_maps reads them (proc_pidinfo)
# peak at 4.7 to 4.9 MiB for a booted microVM of test_api.py and at 5.02
# to 5.19 MiB where the monitor trips: Firecracker's text 2.3 to 2.5 MiB,
# malloc 1.4 to 1.6 MiB, thread stacks 0.2 to 0.35 MiB; an idle Firecracker
# holds 3.0 MiB. Apple silicon maps 16 KiB pages, where Linux's aarch64 and
# x86_64 hosts map 4 KiB ones, so every page a thread, an allocation or a
# code path touches costs four times as much. A pmem device whose file is
# also a drive's counts the file's pages the drive read: macOS reports a
# shared file mapping's resident pages per file, not per process (14 MiB of
# pmem in test_get_full_config_after_restoring_snapshot, whose guest never
# touches the pmem device). The same holds for Firecracker's binary, and
# its text was the largest part: Linux counts a file mapping's pages the
# process mapped (smaps Rss, present page-table entries: fs/proc/task_mmu.c
# smaps_pte_entry), macOS the file's pages in the buffer cache (XNU
# osfmk/vm/bsd_vm.c fill_procregioninfo -> vm_map_region_look_for_page,
# vm_page_lookup in the file's object). The user mode's stand-in ran every
# Firecracker of the session from one binary, so each counted the code all
# of them ran (measured, idle Firecracker without a guest: 5.22 MiB from a
# binary all in the cache, its binary's mappings 3.84 MiB; 2.84 MiB from
# the stand-in's copy in the jail, now a clone with no page cached, as
# upstream's jailer copies the binary into each jail). wick_macos.memory_maps
# now reads the regions in the footprint mode (vm.self_region_footprint, which
# a process sets for itself: XNU vm_map_region_walk then asks the target's
# pmap per page), so a page counts when Firecracker has it mapped, as on
# Linux (measured: the idle Firecracker's binary 0.92 MiB, 2.25 MiB in all,
# from a binary all in the cache). Run with both (clean tree, m2-queue):
# the monitor still trips, at 5.03 to 5.44 MiB in most tests and at 6.48
# to 6.91 MiB in test_vsock_epipe and test_vsock_bare_pause_resume, so what
# is left is not the binary's cached pages. To find: which regions hold it
# (the regions at the trip, in both modes). Only a test whose every failing
# phase failed with this error is excused.
all bug failure:host_tools.memory.MemoryUsageExceededError
