# Upstream's memory monitor (host_tools/memory.py) fails a test whose VMM
# holds more than 5 MiB resident besides guest memory (7 MiB while a
# snapshot is taken), counted as Linux counts it: the pages of every
# mapping present in the process's page tables (smaps Rss, fs/proc/
# task_mmu.c smaps_pte_entry). wick_macos.memory_maps counts the same,
# by the page tables (vm.self_region_footprint, which a process sets for
# itself: XNU vm_map_region_walk then asks the target's pmap per page),
# with the pages the host compressed: smaps leaves swapped pages out of Rss,
# on hosts that do not swap the VMM out, where macOS compresses whenever the
# host is short of memory, so a budget of present pages alone could be met
# by the host's pressure. The monitor keeps the VMM's memory in two parts.
#
# The platform's part, not a failure: the system libraries' pages the
# process mapped from the dyld shared cache. A macOS process cannot do
# without them (Apple QA1118: no statically linked binaries); upstream's
# static Firecracker carries its libc in its own text. The count is the
# process's own: 4.48 MiB on an idle Firecracker without a guest,
# unchanged while other programs ran library code Firecracker never runs,
# and the phys_mem ledger (task RSS) is the sum of both parts. It is
# 4.64 MiB in every one of 77 microVMs with a guest (m2-parts, wick
# 8d577b7, and m2-parts2, d706d9a; macOS 27.2), and the monitor holds it to a ceiling of 5 MiB
# for macOS 27 (wick_macos.SHARED_CACHE_CEILING_MIB; a macOS major not
# measured fails every monitored test, saying so). get_resident_memory, the
# RSS the balloon tests read, leaves the part out and holds it to the same
# ceiling (wick_macos.shared_cache_part: one definition for both).
#
# The VMM's own part, the bug: every mapping outside the shared cache,
# held to upstream's 5 and 7 MiB. In m2-parts2 (d706d9a, with the pages
# the host compressed) it is 4.28 to 6.36 MiB (median 5.05; m2-parts,
# present pages only, 4.16 to 7.92): the binary's text the VM ran, 1.9 to
# 2.2 MiB; libmalloc's small zone (VM_MEMORY_MALLOC_SMALL) 1.7 to 2.0 MiB;
# malloc's other zones 0.65 to 0.7 MiB; thread stacks 0.4 MiB (m2-mem's
# region dumps). In the vsock tests the small zone held vsock's 64 KiB
# per-connection TX buffers, which Firecracker fills when a write to the
# host's socket would block, with xnu's 8 KiB AF_UNIX send buffer where
# Linux's is 208 KiB. Since 49998df every AF_UNIX stream starts with
# Linux's: test_vsock_epipe's peak 4.73 to 5.05 MiB (median 4.91, no TX
# buffer, 3 of 10 over 5 MiB by at most 48 KiB), was 5.2 to 9.4 (median 8.3,
# 50 TX buffers) (A/B at c9b2c5c, 10 microVMs each, sampling past 5 MiB).
# In run mac1-vsock-balloon-ff84c70 (test_vsock.py and test_balloon.py at
# ff84c70) test_vsock.py's tests over the budget went from 17 (m2-parts2,
# d706d9a) to 10, and the kills inside a test from 5 to 1
# (test_vsock_transport_reset_g2h[PCI_ON-2vcpu], after 2 of its 5
# restores); those 10 trip at 5.02 to 5.55 MiB. What remains is under study,
# not explained. The 7 under the budget in that run (test_vsock, both
# variants; the PCI_OFF variants of test_vsock_epipe,
# test_vsock_bare_pause_resume, test_snapshot_restore_with_inflight_vsock_tx
# and test_device_reset; test_vsock_transport_reset_h2g[PCI_OFF-1vcpu]) are
# at the margin: under budget in 1 of 1 runs at ff84c70, so the count below
# stays m2-parts2's. Upstream's message names the threshold in force when
# check_samples raises (host_tools/memory.py:179), 7 MiB once the test took
# a snapshot after the trip, not the 5 MiB the sample crossed (:116): "5.09
# MiB exceeded maximum threshold (7.0 MiB)" is a 5 MiB trip.
# Apple silicon maps 16 KiB pages, where Linux's
# hosts map 4 KiB ones, so every page a thread, an allocation or a code
# path touches costs four times as much. Earlier measurements that counted
# cached file pages (a pmem file's, the binary's own) are superseded: in
# the page tables they count only as mapped. Only a test whose every failing phase failed
# with this error is excused. Upstream raises it when a microVM is killed
# (microvm.py kill, check_samples): a test that kills one inside its body
# stops there, and its steps after that kill did not run, untested rather
# than passed.
# Guest memory a balloon's discard split is counted as guest memory again.
# The discard maps fresh pages over the range (the compatibility libc's
# MADV_DONTNEED). The harness read the guest region in pieces two ways:
# the fresh pages are SM_EMPTY among the SM_TRUESHARED ones
# Hypervisor.framework holds, and it kept regions of another share mode
# apart; and its walk of the regions, one proc_pidinfo lookup each (XNU
# osfmk/vm/bsd_vm.c fill_procregioninfo), met a region replaced between
# two lookups, which came back starting before the walk's position. So
# upstream's size rule (memory.py is_guest_mem) knew none of the pieces,
# and the guest's pages in them counted as the VMM's own: 29.2 to 31.2 MiB
# in 4 of 84 microVMs of test_reinflate_balloon, test_deflate_on_oom,
# test_memory_scrub and test_device_reset (runs mac9-split-1 to -6, with
# and without the libmalloc configuration alike; mac9-raw3-1 showed the
# walk's overlap of 768 KiB, and a second walk one 256 MiB region). It
# merges as Linux merges the areas, by everything but the share mode, a
# shared mapping apart, and takes a walk that met a change again
# (memory-selftest.py's punch, churn and share checks): 0 of 112 microVMs
# of those four tests over 5 MiB after, at most 4.78 MiB (mac9-fixed-1 to -8).
# Only the count was wrong: the guest reads its pages and the host the same
# ones after a discard (test_madvise_dontneed_replaces_guest_pages,
# `boot-test balloon`).
# excused: at least 19 (run m2-parts2 at d706d9a): pass their own assertions up to the memory budget of the VMM's own part, which fails them in the teardown or, in 5, at a kill inside the test, whose later steps then did not run (test_vsock_transport_reset_h2g, all four, before their restore; test_vsock_transport_reset_g2h[PCI_ON-2vcpu] after 2 of its 5 restores)
all bug failure:host_tools.memory.MemoryUsageExceededError

# The test sizes a balloon from its first reading R (test_balloon.py: 256 MiB
# minus get_resident_memory minus 50 MiB), runs fillmem 128 in the guest (it
# goes on after ssh's 1 s timeout, which drops only the local client of the
# ControlMaster) and, 5 s later, wants the balloon smaller. A guest deflates
# on OOM only: Linux v6.1's driver registers an OOM notifier for
# VIRTIO_BALLOON_F_DEFLATE_ON_OOM (drivers/virtio/virtio_balloon.c :927-930)
# that gives back VIRTIO_BALLOON_OOM_NR_PAGES, 256 pages (:30, :834-844), per
# out_of_memory() call, which runs the notifiers before it picks a victim
# (mm/oom_kill.c :1114); the free page shrinker is for FREE_PAGE_HINT only
# (virtio_balloon.c :895-922), which the test does not turn on. So the guest
# must run out of memory: fillmem's 128 MiB must exceed what the guest has
# available after the inflation. The variant without deflate_on_oom passes.
# Measured, six diagnostic runs (mac9-dfd-b, at d1fae5e with the guest's
# /proc/meminfo and /proc/vmstat read after the inflation and after fillmem,
# load 14 to 18): MemAvailable after the inflation 122.5 to 126.8 MiB; fillmem
# succeeded every time, the guest reclaiming 55 to 63 MiB of page cache;
# oom_kill 0; balloon_deflate 0 pages in the three failures and 256 or 512 in
# the three passes (one or two out_of_memory() calls at the end). The guest
# does not run out of memory, so it has nothing to deflate; the device sees
# what it sends. In Linux CI (run 43605802557, x86_64, its x86 guest) R is 112
# to 118 MiB, the balloon 91 to 97 MiB, and it deflates 34 to 38 MiB, so about
# 93 MiB was available there; ten runs of each here (mac9-deflate-on-knobs-1
# to -10 and mac9-deflate-on-noknobs-1 to -10, alternating, and
# mac9-deflate-off-noknobs-1 to -10, at 8540847, load 12 to 21): PCI_ON 9 of
# 10 passed, 8 of 10 with libmalloc's configuration on a test-only branch (the
# VMM's own part 4.64 to 4.78 MiB, and 4.03 to 4.09 with it), PCI_OFF 6 of 10,
# R 142 to 147 MiB, the balloon 63 to 68 MiB and the outcome not following it:
# a coin toss at a margin of a few MiB. What R holds on this aarch64 guest
# (mac9-touched-1, six microVMs: the guest's pages in use by /proc/kpageflags,
# and the pages it wrote, the non-zero 4 KiB pages of a full snapshot's memory
# file): about 4.6 MiB of VMM; 123.2 MiB of guest pages in use, 123.7 MiB in
# 16 KiB frames, so the host's 16 KiB pages add 0.5 MiB; 8.5 to 10.7 MiB of
# frames all free but written, the same in 4 KiB pages, which a Linux host
# holds too; the guest's page cache, about 55 MiB, in use but reclaimable; and
# about 4 MiB of frames with no page in use and none written. A read is enough
# to make this host hold a page (mac9-readonly-1: the guest read 128.3 and
# 133.7 MiB of its free frames through /proc/kcore, writing nothing, and R
# rose 119.8 and 123.2 MiB): XNU has no shared zero page for anonymous memory,
# an absent page is a zero-fill fault whatever the access (xnu-12377.121.6
# osfmk/vm/vm_fault.c :6176, VM_PAGE_GRAB_ZERO_FILL :6241-6244), where Linux
# maps the zero page for a read (mm/memory.c :4088; KVM faults without
# FOLL_WRITE on a read, virt/kvm/kvm_main.c hva_to_pfn_slow :2514-2546) and
# Rss leaves it out (fs/proc/task_mmu.c smaps_pte_entry). The ~4 MiB set is
# not split between pages read and pages zeroed and freed. So the part of R a
# Linux host would not hold is at most about 5 MiB: about 1.2 MiB of VMM

# memory entry above) or upstream's sizing for aarch64 guests. Listed until

# Not an entry, a residual to watch for: screen's terminal. XNU can give two
# terminals opened at the same moment the same minor (xnu-12377.1.9
# bsd/kern/tty_ptmx.c ptmx_clone); the loser's open fails with EREDRIVEOPEN,
# which vn_open_auth retries 10 times and then returns as errno -6, logging
# "vn_open_auth: reached max_retries error -6" (bsd/vfs/vfs_vnops.c). Linux
# takes the index from an IDA and has no such failure (fs/devpts/inode.c
# devpts_new_index). Each microVM's screen 5.0.2 opens its window's terminal
# with openpty (src/pty.c OpenPTY) in its back end, after `screen -dmS` has
# returned (src/screen.c: the front end exits after the fork, then
# MakeWindow), so a lock around the screen call would not cover it. With -n 2
# two screens rarely open at once (16 processes opening 400 terminals each
# lost none here; 32 opening 300 each lost 18 to 36), and none has failed
# so far. If a test fails because its screen session is gone and the
# screen log says "Sorry, could not find a PTY or TTY.", this is why
# (`/usr/bin/log show --predicate 'process == "kernel" AND eventMessage
# CONTAINS "max_retries"'` shows it); vmm's sandbox tests serialize their
# own opens (overlay/vmm/ext/sandbox.rs pty()).
